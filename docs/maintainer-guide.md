# Maintainer guide

A worked example: packaging a hypothetical `mitos-widget` (a small Rust
binary crate) from scratch, including the one thing the README's
quickstart glosses over — a build that needs more than the shared
`cargo` template.

## 1. Create the recipe

```sh
mkdir -p packages/applications/mitos-widget
```

`packages/applications/mitos-widget/recipe.toml`:

```toml
name = "mitos-widget"
version = "0.1.0"
description = "A small example widget."
category = "applications"
channel = "testing"
inherits = "cargo"

[source]
git = "https://github.com/example/mitos-widget"
rev = "v0.1.0"
```

That's it if `cargo install --path . --root "$MITOS_PAYLOAD_DIR/usr"`
(the inherited template — see `recipes/README.md`) is genuinely all this
package needs. Most binary crates are exactly this short.

## 2. When the template isn't enough

Say `mitos-widget` needs its default config file installed to
`/etc/mitos-widget/config.toml` too, which `cargo install` won't do for
you. Give the recipe its own `build.steps` instead of `inherits` — copy
the template's line and add to it, rather than fighting `inherits`
(remember: a recipe's own non-empty `build.steps` always wins over
whatever `inherits` would have supplied, so there's no conflict, just an
explicit full list instead of an implicit one):

```toml
[build]
steps = [
    "cargo install --path . --root \"$MITOS_PAYLOAD_DIR/usr\" --locked",
    "install -Dm644 config.default.toml \"$MITOS_PAYLOAD_DIR/etc/mitos-widget/config.toml\"",
]
```

`inherits` can stay in the file (harmless — `Recipe::resolve` only
consults it when `build.steps` is empty) or be removed; leaving it as a
comment noting which template this started from is often clearer for
the next person than deleting it outright.

## 3. Build and check it locally

```sh
cargo build --release
target/release/mitos-build-package --recipe packages/applications/mitos-widget/recipe.toml
```

Watch for the archive path and payload sha256 printed at the end.
Sanity-check the payload layout before going further:

```sh
tar -tzf repositories/testing/packages/mitos-widget-0.1.0.mpkg
```

## 4. Metadata and index, for local testing

```sh
target/release/mitos-generate-metadata \
    --archive repositories/testing/packages/mitos-widget-0.1.0.mpkg \
    --base-url http://localhost:8000 \
    --out repositories/testing/metadata

target/release/mitos-generate-index --channel testing
```

Point a local `mitos-pkg` install at `http://localhost:8000/index.json`
(serving `repositories/testing/` with any static file server) to test
an actual install end to end before opening a PR.

## 5. Requesting a community signer

If this is a `packages/applications/` package you intend to maintain
long-term (not just a one-off), open an issue asking for a community
signer name — see `keys/README.md`'s table for the naming convention
(one name per maintainer or project, e.g. `community-<your-handle>`). A
maintainer generates the keypair, gives you the seed privately (never
committed — see `SECURITY.md`), and adds your `<name>.pub` to this
repository. From then on, your `recipe.toml` sets
`signer = "community-<your-handle>"` and you run `mitos-sign-package`
with your own seed before each release.

## 6. Open the PR

Recipe file(s) only — never a seed, never a built `.mpkg` unless a
maintainer has explicitly asked for one to debug a CI-only failure
(`repositories/` content is generated by CI, not meant to be hand-
committed in a PR). See `CONTRIBUTING.md` for the rest of the checklist.
